# التخزين المحلي بملف JSON — 2026-10-14

## القرار

أُلغي الاعتماد على أي قاعدة بيانات أو خدمة تخزين خارجية (Turso/libSQL، Upstash Redis / Vercel KV، Vercel Blob،
ونقطة HTTP للقطة). صار التخزين بالكامل **ملف JSON محليًا مهيكلًا** يُكتب بطريقة ذرّية، ولا يحتاج المشغّل إلى أي
إعداد أو متغير بيئة أو توكن أو خطوة ربط يدوية.

## أين يُحفظ الملف

| بيئة التشغيل | المسار | الدوام |
|---|---|---|
| خادم عادي / حاوية / `next start` / `npm run sync` | `data/gateway-store.json` | يبقى بعد إعادة التشغيل |
| Vercel / Lambda / Netlify | `<os.tmpdir()>/nemo-gateway/gateway-store.json` (`/tmp`) | ذاكرة للنسخة الدافئة فقط |
| اختياري | `NEMO_DATA_DIR/gateway-store.json` | حسب المجلد |

`data/gateway-store.json` المُضمَّن في حزمة النشر يبقى بذرة للقراءة فقط (لا يُكتب داخل الحزمة على Vercel).

## الكتابة الذرّية

`lib/db/atomic-file.ts`:

1. كتابة المحتوى إلى ملف مؤقت باسم فريد (`<file>.<pid>.<random>.tmp`).
2. `fsync` على الملف المؤقت.
3. `rename` فوق الملف الأصلي (عملية ذرّية داخل المجلد نفسه).
4. عند أي فشل: إغلاق المقبض وحذف الملف المؤقت، ويبقى الملف الأصلي كما كان.

اختبار `tests/local-json-store.test.ts` يحاكي فشل `rename` ويتحقق من بقاء الوثيقة السابقة سليمة وعدم بقاء مؤقتات.

## الملف التالف

عند القراءة يُتحقق من الشكل (`isGatewayDatabaseShape`). الملف المبتور أو الغريب يُنقل إلى
`gateway-store.json.corrupt-<timestamp>.json` ويبدأ المخزن من المصدر التالي (الذاكرة أو البذرة)، فلا يتوقف النظام
ولا يحتاج تدخلًا يدويًا. الملف المنقول محفوظ للفحص.

## عقد الاستجابة لمسارات الكرون والمزامنة

| المسار | الرمز | `ok` | الحالة الفعلية |
|---|---|---|---|
| `GET/POST /api/cron/update-matches` | 200 دائمًا | `true` دائمًا | `status` = `ok` / `degraded`، و`syncOk`، و`durable`، و`warnings` |
| `GET/POST /api/cron/sync` | 200 دائمًا بعد المصادقة | `true` دائمًا | كما أعلاه |
| `GET/POST /api/cron/sync-news` | 200 دائمًا بعد المصادقة | `true` دائمًا | كما أعلاه |
| `POST /api/admin/news/sync` | 200 دائمًا بعد المصادقة | `true` دائمًا | كما أعلاه |
| `GET /api/health` | 200 دائمًا | حسب الفحص | `checks.*` (يقرأ الملف ويتحقق من العدّادات) |

**لماذا `ok: true` مع `status: "degraded"`؟** الطلب أراد أن يكون رمز النجاح لا يتعطل بسبب إعداد التخزين، لذلك صار
`ok` يعني "استجاب المسار ونُفّذ الإجراء دون انهيار". الفشل الحقيقي يظهر في `status` و`syncOk` و`warnings`، ويجب أن
تُراقَب هذه الحقول لا رمز HTTP.

**ما الذي لم يتغير عمدًا؟** مسارات المزامنة المحمية ما زالت تتطلب `CRON_SECRET` (أو `NEMO_INGEST_TOKEN`). بدونه ترجع
`500 Misconfigured` ولا تُنفّذ شيئًا. فتحها للعامة كان سيسمح لأي طرف باستهلاك حصص المزودين، لذلك لم تُفتح دون قرار صريح.
المسار `/api/cron/update-matches` عام حسب التصميم الموثّق في README.

## الحدود المعروفة

- على Vercel لكل نسخة `/tmp` خاص بها: بيانات كتبتها نسخة قد لا تراها نسخة أخرى، وتُفقد عند البدء البارد. هذا ما يعنيه
  `durable: false` ولا يُخفى.
- لا يوجد قفل بين النسخ المتوازية؛ الكتابة الأخيرة تفوز.
- الحصص وحدود المزودين لم تتغير.
